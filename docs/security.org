* Explain like I'm 5: how the security works
:PROPERTIES:
:CUSTOM_ID: explain-like-i-m-5-how-the-security-works
:END:

Imagine you want to send a secret note to a friend through a post office you do
not trust, and you also want your friend to be sure the note really came from
you and was not edited on the way.

1. *You put the note in a box and lock it.* The box is locked with your
   =encryption-key=; only someone holding that key can open it. A person
   handling the mail sees a solid box, not words.
2. *You wrap the whole box in a second, different lock.* That second lock is
   the =signing-key=, a separate key on purpose: two locks, two keys, no single
   point of failure.
3. *You write a label on the outside:* who the note is for, when you made it,
   and when it should be thrown away. The second lock seals the label together
   with the box, so editing the label, say to "keep this forever" instead of
   "throw this away tomorrow", means the lock does not open at all.
4. *The whole parcel is written in a plain alphabet* (hexadecimal), so it can
   travel through email, URLs and cookies without breaking.

Five things follow from that:

- *The keys are the secret, not the method.* Everyone, including anyone reading
  this file and every line of bewaking's source code, can know exactly how the
  box is built; that is on purpose. See
  [[#what-the-source-code-gives-an-attacker][What the source code gives an
  attacker]].
- *Every box looks different.* Each seal draws fresh random numbers, so sealing
  the same note twice produces two completely different parcels, and nobody
  watching the mail can tell which two parcels carry the same note.
- *Every edit is noticed.* Change one character of the box or of the label and
  the parcel refuses to open; you cannot swap the note, correct a date, or swap
  which key the label claims was used.
- *Old parcels do not need re-sending when you rotate keys.* The label says
  which key was used, so the right key can be picked automatically (see
  [[file:sealing.org::#key-rotation][key rotation]]).
- *A parcel can be given a "throw away after" date* that the recipient's
  server checks before it opens anything, so a stolen parcel stops working on
  its own.

And the one thing this cannot do:

- *It cannot protect a weak key.* If your =encryption-key= is =hunter2=, a
  determined attacker can simply guess it. All the strength comes from the keys
  being long, random and secret, so use long random values, keep them out of
  source control, logs and screenshots, and never reuse one pair across
  development and production. See
  [[#choosing-and-keeping-keys][Choosing and keeping keys]].

* Security notes
:PROPERTIES:
:CUSTOM_ID: security-notes
:END:

- *No subprocesses, so no shell surface.* Keys and payloads are never
  interpolated into a command line; they stay in Guile values and are handed
  straight to libgcrypt. There is nothing to quote, nothing that can be read
  from ~/proc/PID/cmdline~, and nothing that a NUL byte or a quote character
  can confuse.
- *No evaluation of decrypted content.* Decrypted payloads are parsed with
  ~read~, which cannot execute code. (Guile also disables the ~#.~ read-eval
  syntax by default.) Whatever was sealed is what comes back, with no wrapper to
  interpret.
- *Malformed input is refused early.* A wrong key surfaces as a padding or
  format error before any payload is parsed, instead of being mistaken for
  valid data. Base64 and Base16 input is validated character by character.
- *Authenticity is checked explicitly, by one mechanism.* Every sealed value is
  a BWK3 envelope, and its authenticity comes from AES-256-GCM, whose tag covers
  the rotation metadata (=key-id=, =created-at=, =expires-at=) as associated
  data. There is no second verification path: a token or object that was edited
  is reported rather than silently accepted, and no field of the metadata can be
  rewritten without invalidating the seal. The format is version-tagged so it can
  evolve, and any tag other than the current one is refused outright.
- *Rotation policies are enforced, not advisory.* An envelope's =expires-at= is
  checked before its plaintext is returned (unless =#:enforce-expiry? #f= /
  =--allow-expired= explicitly asks otherwise), =#:max-age-seconds= bounds how
  old data may be, and a keyring entry's =not-before= / =not-after= window
  restricts when a key may be used. Expired data is refused rather than quietly
  decrypted, and a retired key stops opening its data at once.
- *A refusal is not an oracle.* An unknown key id, a missing keyring entry, a
  retired or not-yet-active key, a wrong key and an altered body all raise the
  same error, and the attempt is made with a placeholder key rather than
  abandoned early. Nothing about a refusal, least of all its message, names a key
  id or enumerates the keyring. Expiry is the one exception, and it is only
  reachable once the tag has shown the envelope to be genuine. See
  [[file:sealing.org::#a-refusal-does-not-enumerate-the-keyring][A refusal does not enumerate
  the keyring]].
- *Obfuscation is not security.* ~string-garble~ / ~string-ungarble~ are
  reversible by design; the real protection comes from the two independent
  AES-256 keys.
- *Key handling is the caller's responsibility.* Keep the ~encryption-key~ and
  ~signing-key~ secret and distinct. Keys are used in-process and never travel
  through a command line, so they do not appear in the process list; they are
  still ordinary Guile strings, so avoid printing or logging them.

* Choosing and keeping keys
:PROPERTIES:
:CUSTOM_ID: choosing-and-keeping-keys
:END:

Everything bewaking promises reduces to one sentence: *the keys are the secret.*
The algorithms, the formats, the source code and this document are all public,
and none of them has to be protected. A key does.

** Use long, random keys
:PROPERTIES:
:CUSTOM_ID: use-long-random-keys
:END:

The keys are ordinary strings, so nothing forces them to be strong, which is one
of the few ways to break the scheme without breaking the code. A good key is at
least 32 bytes from a cryptographically strong source:

#+begin_src shell
# 32 random bytes, hexadecimal: 64 hex characters, 256 bits.
openssl rand -hex 32
# or, without OpenSSL:
head -c 32 /dev/urandom | base16 -w 0
#+end_src

A UUID (as used in the examples above for readability) carries about 122 bits of
randomness and is acceptable; a word, a date, a project name, or a password you
can remember is not. Do not stretch a weak key by hashing it or prefixing it with
a constant; that adds no entropy. If a human-memorable secret must be the key,
seal with ~#:kdf 'argon2id~ (64 MiB, 3 passes by default) instead of the default
PBKDF2: the derivation is meant to slow a guessing attacker down, and PBKDF2's
10 000 iterations are far too cheap for a passphrase (see
[[#what-the-source-code-gives-an-attacker][What the source code gives an
attacker]]).

** Keep them secret and distinct
:PROPERTIES:
:CUSTOM_ID: keep-them-secret-and-distinct
:END:

- The ~encryption-key~ and the ~signing-key~ must be two *different* values. If
  they are equal, the inner and outer layers share a secret, and an attacker who
  learns one has learned both.
- Give every environment (development, staging, production) its own pair. A
  shared development key is a production key handed to every developer.
- Never commit a key. Not in source, not in a test, not in a config file, not in
  a container image, not in a screenshot of a terminal.
- Prefer the environment (=BEWAKING_ENCRYPTION_KEY=,
  =BEWAKING_SIGNING_KEY=) or a file (=--encryption-key-file=,
  =--signing-key-file=) over a command-line argument: environment variables and
  files are not copied into your shell history or shown in a process list.
- Do not log keys, and do not log tokens either; a token is a bearer credential.
  The exception is the envelope *header*, which ~envelope-metadata~ reads without
  any key and which carries only the key id and timestamps.

** Plan for rotation, and for compromise
:PROPERTIES:
:CUSTOM_ID: plan-for-rotation-and-for-compromise
:END:

- Give each key pair a key id and seal new data with the current one; a
  [[file:sealing.org::#key-rotation][keyring]] lets old data keep opening without a migration.
- A keyring entry's =not-before= / =not-after= window is how you retire a key:
  data sealed with it stops opening, immediately.
- If a key does leak, rotate first and investigate second: roll in a new pair,
  retire the old entry, and let short token lifetimes bound the exposure. Keys
  used in-process are not in ~ps~ output, but they may be in shell history if
  they were passed on a command line, and they are plain Guile strings in memory
  while the process runs; there is no way to wipe them, so keep the process's
  memory as uninteresting as its disk.

* What the source code gives an attacker
:PROPERTIES:
:CUSTOM_ID: what-the-source-code-gives-an-attacker
:END:

bewaking is free software. Assume the worst case, because it is the real case:
*the attacker has read every line of this repository.* They have the algorithms,
the envelope layout, the constants, the garbling routine, the test suite and the
reference vectors. They also have as many copies of any token or sealed object
they can capture, and they can edit one as much as they like. This section states
what that buys them, and what it does not.

** What they get: a clear view of a public format
:PROPERTIES:
:CUSTOM_ID: what-they-get-a-clear-view-of-a-public-format
:END:

- They can parse any token, and via ~envelope-metadata~ read its version, key id
  and timestamps *without any key*. That is deliberate: those fields are what
  rotation and log review work from, and they contain no secret.
- They know exactly which algorithms protect the data (AES-256-CBC inside,
  AES-256-GCM outside), how the keys are derived (PBKDF2 or Argon2id, and with
  which parameters, because the sealed body records them), and where every byte
  sits. None of that is a secret in a modern design; this is Kerckhoffs's
  principle, and the alternative (security through a hidden format) would be
  broken the moment somebody published the code.
- They know the obfuscation step is obfuscation. So do you: it exists to leave
  two independent encryptions between the plaintext and a reader, not to resist
  someone with a debugger.

** What they do not get: the keys, and therefore none of the values above
:PROPERTIES:
:CUSTOM_ID: what-they-do-not-get-the-keys-and-therefore-none-of-the-values-above
:END:

- *No decryption.* The body is AES-256-GCM under a key derived from the signing
  key, and the inner AES-256-CBC layer is only reached after that tag verifies.
  Without the keys, the ciphertext and any "ungarbling" the attacker performs on
  it stay ciphertext. There is no source-level shortcut to AES-256.
- *No forgery.* Every attempt starts from a genuine envelope, and the tag covers
  the ciphertext *and* the header. Flipping any digit of a real envelope,
  relabelling its version, swapping its key id, backdating =created-at=, or
  extending =expires-at= all make the tag fail; the suite checks each of these,
  including an exhaustive digit-by-digit mutation of a real token. Knowing the
  format is what makes those edits easy to *try*, and the tag is what makes each
  of them fail.
- *No swapping a body between headers.* The header is the cipher's associated
  data, so a valid body moved under a different key id, version or expiry does
  not open: the pair (header, body) is the unit that is authenticated.
- *No oracle to lean on.* A wrong key, an edited ciphertext, edited associated
  data and an unresolvable key id are indistinguishable: the envelope layer
  raises one refusal for all of them, and it raises rather than returning
  anything. The tag is checked by libgcrypt's ~gcry_cipher_checktag~ before a
  byte of plaintext is returned, the inner CBC layer's padding error is only
  reached once that tag has been accepted, and an unresolvable key id is tried
  against a placeholder instead of being answered early, so neither the padding
  error nor the keyring is a signal an attacker can probe. That is what makes a
  padding-oracle attack and keyring enumeration unavailable here rather than
  merely awkward. The raw =GCM authentication failed= text still exists for
  direct users of the ~(bewaking crypto)~ primitive, where it is the honest
  answer and no key id is involved; the envelope layer does not pass it on.
- *No code execution from decrypted data.* Payloads are parsed with ~read~, not
  ~eval~, and Guile's ~#.~ read-eval syntax is off by default (verified in the
  suite), so a sealed value cannot smuggle code into the process that opens it.
- *No shell.* There is no subprocess and no command line for a key or a payload
  to be interpolated into, so there is nothing to quote and nothing to read out
  of ~/proc=.
- *No hardcoded secret to find.* The source contains no key material: the keys
  in this document and in the test suite are labelled examples, and the suite's
  fixtures are deliberately distinct from any real pair.

** Where knowing the source does help: the honest list
:PROPERTIES:
:CUSTOM_ID: where-knowing-the-source-does-help-the-honest-list
:END:

- *Offline guessing, if the key is weak.* The source (and the sealed body) tells
  an attacker the exact derivation cost, so a low-entropy key (a passphrase, a
  pattern, a reused string) can be brute-forced offline against a captured token
  without touching your server. This is the one place source knowledge is a real
  advantage, and the whole answer is
  [[#choosing-and-keeping-keys][long random keys (or Argon2id for a
  passphrase)]].
- *A chosen key-derivation cost.* The Argon2id parameters travel inside the
  sealed body, so a crafted body can name a deliberately expensive derivation
  (up to the validated bound of 4 GiB of memory and four billion passes) and
  make the *receiver* spend that much work before the tag is even checked, so
  source knowledge turns into a small denial-of-service primitive. The bound is
  enforced *before* anything is allocated, so the worst case is capped rather
  than unbounded, but the cap is high enough to matter. The default PBKDF2 cost
  is fixed at 10 000 iterations, so tokens sealed with the default are not
  affected; if your application accepts Argon2id bodies from untrusted clients,
  keep sealing with the default, or reject tokens that arrive without a prior
  authenticated step. The suite pins this: a payload whose recorded cost is
  above the bound is refused with a parameter error (not by running the
  derivation), while a cost inside the bound is derived and then fails the tag.
- *Which key ids exist: closed.* Every "we could not open this" cause returns the
  same error, and an unresolvable key id is opened against a placeholder key
  instead of being abandoned early, so the refusal does not differ in message or
  in work. The key id still appears in the *header*, where ~envelope-metadata~
  reads it without any key, but that is a claim to log, not a decision, and it is
  not a statement about what the deployment's keyring contains.
- *Replay.* A captured, still-valid token is a bearer credential: the source
  cannot change that, because stateless sessions have no server-side list to
  revoke from. Short lifetimes, key retirement and an optional denylist are the
  mitigations, and they are matter-of-fact, not secret.

** The short version
:PROPERTIES:
:CUSTOM_ID: the-short-version
:END:

An attacker with the source, the format and any number of captured tokens, but
without the two keys, cannot read a sealed value, cannot forge one, cannot alter
one field of one, and cannot derive a key from what they hold. That is what
"the keys are the secret" means here, and it is what the suite pins down: the
sealed value leaks nothing, every edit of a genuine value is refused, and the
same plaintext never seals twice.
