bewaking provides functionalities to (double) encrypt and decrypt data, aided by a custom obfuscation algorithm.

It also provides a domain-specific language (DSL) to be used for authorization, authentication and token generation for your Guile Scheme projects, including a simple user permission system, and a password-strength module to measure, classify and generate passwords without leaving Guile.

* About bewaking
:PROPERTIES:
:CUSTOM_ID: about-bewaking
:END:

/bewaking/ means surveillance in the Dutch language.

All of its cryptography (AES-256-CBC, AES-256-GCM, PBKDF2, Argon2id,
HMAC-SHA256, Base16 and Base64) runs inside the Guile process, so bewaking
spawns no subprocesses, needs no external command-line tools, and produces the
same payload layout as ~openssl enc -aes256 -pbkdf2~.

There is exactly one envelope format, =BWK3=: it is the only one bewaking writes
and the only one it reads. Anything else, including an unstructured string that
merely looks like a token, is refused rather than guessed at.

You can find the technical Guile Scheme API documentation for Bewaking here:

https://jointhefreeworld.org/api-docs/bewaking/API.html

*** Note on the wire format
:PROPERTIES:
:CUSTOM_ID: note-on-the-wire-format
:END:

The inner layer of every sealed body is exactly what
~openssl enc -aes256 -pbkdf2 -a -A -k KEY~ produces, and bewaking reads that
format back: an 8-byte salt in a ~Salted__~ header, a 32-byte key and a 16-byte
IV derived with PBKDF2-HMAC-SHA256 over 10000 iterations, and AES-256-CBC with
PKCS#7 padding. Data sealed by the OpenSSL CLI, or by any other implementation
of that format, opens as well. The corresponding reference values live in the
test suite, so the compatibility is checked without needing OpenSSL installed.

The outer, authenticating layer is AES-256-GCM.

* Quick start
:PROPERTIES:
:CUSTOM_ID: quick-start
:END:

#+begin_src scheme
(use-modules (bewaking bewaking))

(define encryption-key "952e0690-6c3b-4828-b191-961bf98d055c") ; 1st seal
(define signing-key    "503f5869-0a3c-4460-971f-5a88662de3fc") ; 2nd seal

(define (get-owner-details)
  '((id . "144959d3-7a8e-455e-b608-31e35145a2fa")
    (email . "joe@example.com")
    (name . "Joe")
    (permissions read-only access-files manage-profile)))

;; 1. Create a token.
(define token (generate-token #:encryption-key encryption-key
                              #:signing-key    signing-key
                              #:get-owner-details get-owner-details))

;; 2. Read it back.
(define payload (decrypt-token #:token token
                               #:encryption-key encryption-key
                               #:signing-key    signing-key))

;; 3. Make authorization decisions.
(has-needed-permissions? #:present (assoc-ref payload 'owner-permissions)
                         #:needed  '(access-files))     ; => #t
(is-token-expired? #:token payload)                     ; => #f
#+end_src

Turning this into a login and protected routes is a thin layer on top of the
token API; see [[#using-bewaking-in-a-web-application][Using bewaking in a web
application]].

* Introduction
:PROPERTIES:
:CUSTOM_ID: introduction
:END:

bewaking's core functionality is generating encrypted tokens and decrypting them and includes a simple permission functionality.

For flexibility and using the power of Lisp, a user's token payload is accepted as thunk argument (lambda with no parameters). Then you can call ~generate-token~ with an encryption key (1st seal), signing key (2nd seal) and a thunk like this. These details will later be used by bewaking in the token.

#+begin_src scheme
(define get-owner-details
  (lambda ()
    `((id . "144959d3-7a8e-455e-b608-31e35145a2fa")
      (email . "joe@example.com")
      (name . "Joe")
      (permissions read-only
                   access-files
                   manage-profile))))
#+end_src

The data that will actually be encrypted looks like this (and this is also the data you get from decrypting a token):

#+begin_src scheme
'((token-data
   (token-type . "bewaking-token")
   (token-id . "123e4567-e89b-12d3-a456-426655440000")
   (token-created-at . 1672531200)
   (token-expires-at . 1672534800))
  (owner-data
   (owner-id . "144959d3-7a8e-455e-b608-31e35145a2fa")
   (owner-email . "joe@example.com")
   (owner-name . "Joe")
   (owner-permissions (read-only access-files manage-profile))))
#+end_src

* Double Encryption and Obfuscation
:PROPERTIES:
:CUSTOM_ID: double-encryption-and-obfuscation
:END:

The code employs a multi-layered approach to secure the token:

1. *First Encryption (Payload Encryption):*
    - The s-expression *payload* (the actual information inside the token, in the form of Lisp (Guile Scheme) code) is first converted into a string and then *Base64-encoded*. Base64 is a way to represent binary data as text, making it safe for transmission over text-based systems.
    - This Base64-encoded string is then encrypted using *AES-256* (a strong encryption standard) with an ~encryption-key~. This is the first layer of real cryptographic protection, making the payload unreadable without the correct key. The encryption runs in-process through libgcrypt, in the exact format the ~openssl~ command line produces. The output of this step is also Base64-encoded.

2.  *Obfuscation (Garbling):*
     - The result from the first encryption (which is already Base64-encoded and encrypted) is then passed through a function called `string-garble`. This function isn't encryption; it's a simple **obfuscation** technique. It takes the string, splits it in half, reverses each half, and then recombines them (second half reversed, then first half reversed). This makes the string look scrambled and harder to read at a glance, but it's not cryptographically secure and can be easily reversed by `string-ungarble`. It adds a minor layer of confusion, not security.

3.  *Second Encryption (Signing/Outer Encryption):*
    - *The *garbled* (obfuscated) string from the previous step is then encrypted *again* using *AES-256* with a *different* key, called the ~signing-key~. This creates the final, external layer of encryption for the token. This layer essentially "signs" and seals the entire encrypted and garbled inner content, further protecting it and making it harder to tamper with.

4. *Second garbling*
   For an added layer of indirection and obfuscation we garble the contents again.

5. *Hexadecimal encoding*:
   - The signed payload (in base64) is finally encoded into a hexadecimal string (in base16) for maximum portability across systems and for an extra layer of indirection.

When decrypting, the process is reversed: the token is first base16-decoded, then ungarbled, decrypted with the ~signing-key~, then ungarbled, then decrypted with the ~encryption-key~, and finally Base64-decoded to reveal the original payload.

*  Auth Token Payload
:PROPERTIES:
:CUSTOM_ID: auth-token-payload
:END:

The *token payload* is essentially the data or information that the token carries. When a token is generated, this is the information that gets secured inside it. In this code, the token payload is a list of key-value pairs (an "association list" in Scheme) that includes:

Data about the token:
-   token-type ::  Always ~bewaking-token~, identifying what kind of token this is, our stamp of approval!
-  token-id ::  A unique identifier for this specific token, generated using a UUID (Universally Unique Identifier).
-  token-created-at ::  The timestamp (time in seconds since the epoch) when the token was created.
-  token-expires-at ::  The timestamp when the token will become invalid, calculated by adding a specified validity period to the creation time. This ensures tokens have a limited lifespan.

The owner:
-  owner-id ::  A unique identifier for the user or entity that owns or is associated with this token.
-  owner-email ::  The email address of the token owner.
-  owner-name ::  The name of the token owner.
-  owner-permissions ::  A list or structure detailing what actions the token owner is allowed to perform.

Before the payload is encrypted, the code checks if these essential fields are present using the ~token-payload-valid?~ function.
If any are missing, it throws an error, indicating that a valid token cannot be generated without complete owner details.

* The token API
:PROPERTIES:
:CUSTOM_ID: the-token-api
:END:

All token functions live in ~(bewaking bewaking)~. Functions whose name starts
with ~unsafe-~ raise errors on failure, while their unprefixed counterparts
catch errors, print a message, and return =#f=.

| Function                  | Arguments                                                                                                                                        | Returns                                     |
|---------------------------+--------------------------------------------------------------------------------------------------------------------------------------------------+---------------------------------------------|
| ~generate-token~          | =#:encryption-key=, =#:signing-key=, =#:get-owner-details=, =#:token-validity-seconds=, =#:key-id=, =#:keyring=, =#:ttl-seconds=, =#:expires-at= | token string, or =#f= on failure            |
| ~decrypt-token~           | =#:token=, =#:encryption-key=, =#:signing-key=, =#:keyring=, =#:enforce-expiry?=, =#:max-age-seconds=                                            | payload alist, or =#f= on failure           |
| ~unsafe-generate-token~   | same as ~generate-token~                                                                                                                         | token string (raises on failure)            |
| ~unsafe-decrypt-token~    | same as ~decrypt-token~                                                                                                                          | payload alist (raises on failure)           |
| ~token-payload-valid?~    | =payload=                                                                                                                                        | =#t= when every required field is present   |
| ~is-token-expired?~       | =#:token=                                                                                                                                        | =#t= when =token-expires-at= is in the past |
| ~token-remaining-seconds~ | =#:token=                                                                                                                                        | seconds left (negative once expired)        |
| ~token-valid?~            | =#:token=                                                                                                                                        | =#t= when well-formed *and* unexpired       |

There is no MAC key in this API. The envelope's integrity is the cipher tag
inside its body, so sealing and opening both need exactly two keys: an
=encryption-key= and a =signing-key=.

*** Checking a token's lifetime
:PROPERTIES:
:CUSTOM_ID: checking-a-token-s-lifetime
:END:

#+begin_src scheme
(is-token-expired? #:token payload)                 ; #f while still valid
(token-remaining-seconds #:token payload)           ; e.g. 604800
(token-valid? #:token payload)                      ; #t
#+end_src

~is-token-expired?~ and ~token-remaining-seconds~ raise an error when the
payload has no numeric =token-expires-at= field. Use these helpers *after*
decrypting a token; passing an arbitrary alist is not meaningful.

These helpers examine the *decrypted payload*, whose expiry comes from
=#:token-validity-seconds=. The envelope itself can carry an independent expiry
(see [[#versioned-and-authenticated-seals][Versioned and authenticated seals]])
via =#:ttl-seconds= or =#:expires-at=;
~decrypt-token~ refuses to open a token whose envelope expiry has passed, so
the two together let you bound a token both by its payload lifetime and by the
rotation policy of the key that sealed it.

* Generic payloads: encrypt-object / decrypt-object
:PROPERTIES:
:CUSTOM_ID: generic-payloads-encrypt-object-decrypt-object
:END:

You are not limited to authorization tokens. Any Scheme datum that ~write~ can
serialize can be sealed with the exact same double-encryption, garbling and
base16 pipeline, and reopened later:

#+begin_src scheme
(use-modules (bewaking bewaking))

(define sealed
  (encrypt-object #:payload '((user . "joe")
                              (age . 42)
                              (roles admin editor)
                              (issued-at . 1672531200))
                  #:encryption-key encryption-key
                  #:signing-key    signing-key))

(decrypt-object #:object sealed
                #:encryption-key encryption-key
                #:signing-key    signing-key)
;; => ((user . "joe") (age . 42) (roles admin editor) (issued-at . 1672531200))
#+end_src

Supported payloads include alists, plain lists, vectors, numbers, strings,
booleans and any nesting of those. The safe ~encrypt-object~ / ~decrypt-object~
return =#f= on failure; ~unsafe-encrypt-object~ / ~unsafe-decrypt-object~ raise.

Decrypted content is parsed with Scheme's ~read~, never ~eval~. Untrusted data
therefore cannot execute code during decryption.

* Versioned and authenticated seals
:PROPERTIES:
:CUSTOM_ID: versioned-and-authenticated-seals
:END:

Sealed tokens and objects are wrapped in a self-describing envelope whose header
also carries *rotation metadata*:

#+begin_src text
BWK3.<key-id>.<created-at>.<expires-at>.<body>
#+end_src

- =BWK3=: the *format version tag*. It leaves room for the format to evolve,
  and says which integrity mechanism the envelope uses.
- =<key-id>=: a short label identifying which key sealed the data (default
  =“default”). It enables [[#key-rotation][key rotation]].
- =<created-at>=: the Unix timestamp (seconds) at which the data was sealed.
- =<expires-at>=: the Unix timestamp after which the data must not be opened,
  or =-= when it never expires.
- =<body>=: the authenticated sealed payload described below.

** Authenticity from the cipher
:PROPERTIES:
:CUSTOM_ID: authenticity-from-the-cipher
:END:

The body is sealed with *AES-256-GCM*, under a key derived from the signing key.
The four header fields above are passed to the cipher as *associated data*, so
the one authentication tag covers the ciphertext *and* the metadata:

#+begin_src text
body = kdf-id(1) | salt(16) | nonce(12) | ciphertext | tag(16)     (Base16)
#+end_src

Only the two keys are needed; there is no MAC key to provision or rotate. Two
properties follow from binding the header to the cipher:

- The header cannot be *read as authentic* before the cipher accepts it.
  ~open-envelope~ decrypts with the tag check built into the operation, so a
  plaintext exists only once authenticity is established; altering =key-id=,
  =created-at= or =expires-at=, including extending an expiry, makes the tag
  fail rather than changing what the envelope means.
- Tampering is *refused*, not reported in detail. The underlying cipher says
  =GCM authentication failed=, which is exactly what a direct user of the
  ~(bewaking crypto)~ primitive sees, because a tag is what tells a wrong key
  from edited data. At the envelope layer, though, ~open-envelope~ deliberately
  answers with one refusal for every "could not open this" cause; see
  [[#a-refusal-does-not-enumerate-the-keyring][A refusal does not enumerate
  the keyring]].

Because the metadata is authenticated, =key-id=, =created-at= and =expires-at=
can still be *audited without any key* through ~envelope-metadata~, which is what
makes log review and rotation tooling possible. Reading the metadata is not the
same as trusting it: ~open-envelope~ is the only place that decides.

** A refusal does not enumerate the keyring
:PROPERTIES:
:CUSTOM_ID: a-refusal-does-not-enumerate-the-keyring
:END:

Every "we could not open this" answer is the same message, on every surface:
the library's error, what ~decrypt-token~ prints, the CLI's message and its exit
code:

#+begin_src text
bewaking: the sealed data could not be opened: unknown, retired or wrong key, or the data was altered.
#+end_src

The key id travels in the clear, so anybody can put any label in a token and
watch how the attempt is refused. If an unknown label failed differently from a
bad tag, or if the message merely named the label, the refusal itself would list
which key ids a deployment configures, which is exactly the reconnaissance key
rotation is supposed to be invisible to.

So an unknown key id, a missing keyring entry, a retired key, a key that is not
active yet, a wrong key and an altered body are one answer. An unresolvable key
id does not even stop the attempt early: the envelope is opened with a freshly
drawn placeholder key that cannot be right, so the work done, and therefore how
long the refusal takes, is comparable to the wrong-key case as well. A retired
key still opens nothing, because the placeholder is not the retired key.

Expiry is the one deliberate exception. It is only reached *after* the tag has
proved the envelope genuine, so telling an operator "this expired" reveals
nothing an attacker could not already read from the envelope's own header with
~envelope-metadata~. Everything else stays deliberately unspecific.

** Rotation metadata: expiry and audit
:PROPERTIES:
:CUSTOM_ID: rotation-metadata-expiry-and-audit
:END:

Pass =#:ttl-seconds= (a lifetime from now) or =#:expires-at= (an absolute
timestamp) when sealing to record an expiry. ~open-envelope~ then refuses to
open data whose expiry has passed, and ~open-envelope~'s =#:max-age-seconds=
adds a blanket “nothing older than this” policy:

#+begin_src scheme
(define sealed (seal-envelope #:plaintext "a shared secret"
                              #:encryption-key k1 #:signing-key k2
                              #:key-id "2026a"
                              #:ttl-seconds (* 24 3600)))   ; good for a day

;; Audit the header with no key at all; useful for tooling and log review.
(envelope-metadata #:sealed sealed)
;; => ((version . "BWK3") (key-id . "2026a")
;;     (created-at . 1791709670) (expires-at . 1791796070))

(envelope-expired? #:sealed sealed)                 ; => #f while it is live
(open-envelope #:sealed sealed                       ; raises once expired
               #:encryption-key k1 #:signing-key k2)
(open-envelope #:sealed sealed #:now some-timestamp  ; deterministic checks
               #:encryption-key k1 #:signing-key k2)
#+end_src

=#:enforce-expiry?= (default =#t=) and =#:allow-expired= on the command line
exist for recovery and audit: they open expired data instead of refusing it.

** Sealing API
:PROPERTIES:
:CUSTOM_ID: sealing-api
:END:

| Function            | Arguments                                                                                                       | Returns                                       |
|---------------------+-----------------------------------------------------------------------------------------------------------------+-----------------------------------------------|
| ~seal-envelope~     | =#:plaintext=, =#:encryption-key=, =#:signing-key=, =#:key-id=, =#:created-at=, =#:expires-at=, =#:ttl-seconds= | envelope string                               |
| ~open-envelope~     | =#:sealed=, =#:encryption-key=, =#:signing-key=, =#:keyring=, =#:enforce-expiry?=, =#:max-age-seconds=, =#:now= | plaintext string (raises on tamper/expiry)    |
| ~sealed-envelope?~  | =sealed=                                                                                                        | =#t= when it is a versioned envelope          |
| ~envelope-metadata~ | =#:sealed=                                                                                                      | alist of version/key-id/created-at/expires-at |
| ~envelope-expired?~ | =#:sealed=, =#:now=                                                                                             | =#t= when the recorded expiry has passed      |

#+begin_src scheme
(define sealed (seal-envelope #:plaintext "a shared secret"
                              #:encryption-key k1 #:signing-key k2))

(open-envelope #:sealed sealed #:encryption-key k1 #:signing-key k2)
;; => "a shared secret"
#+end_src

** Key rotation
:PROPERTIES:
:CUSTOM_ID: key-rotation
:END:

Every envelope records the key id that sealed it. Provide a *keyring*, an alist
mapping key ids to their key entries, and bewaking selects the right keys
automatically when opening. New data is sealed with a chosen key id.

#+begin_src scheme
(define keyring
  '(("2026a" (encryption-key . "e1") (signing-key . "s1"))
    ("2025b" (encryption-key . "e0") (signing-key . "s0"))))

;; Seal with the current key.
(define sealed (encrypt-object #:payload '((plan . pro))
                               #:keyring keyring
                               #:key-id "2026a"))

;; Open with the keyring; the envelope's own key id selects the keys.
(decrypt-object #:object sealed #:keyring keyring)
;; => ((plan . pro))
#+end_src

To rotate keys: add the new key under a fresh key id, start sealing new data
with it, and keep the old keyring entry until the last token sealed with it has
expired. A keyring takes precedence over explicit keys; the same path works for
~generate-token~, ~encrypt-object~, ~decrypt-token~ and ~decrypt-object~.

*** Enforcing a rotation schedule
:PROPERTIES:
:CUSTOM_ID: enforcing-a-rotation-schedule
:END:

A keyring entry may carry a validity window, so a rotation policy is enforced at
run time instead of relying on discipline:

#+begin_src scheme
(define keyring
  '(("2026a" (encryption-key . "e1") (signing-key . "s1")
             (not-before . 1780000000))
    ("2025b" (encryption-key . "e0") (signing-key . "s0")
             (not-after . 1790000000))))

;; Raises while the window rejects the key: the data is sealed with a key that
;; is not active yet, or has been retired, and cannot be opened at all.
(decrypt-object #:object sealed #:keyring keyring)
#+end_src

=not-before= refuses to use a key before it is activated; =not-after= refuses
once it is retired. Combine the two with the per-envelope =expires-at= to bound
data to the lifetime of the key that protects it.

*** One format, one integrity check
:PROPERTIES:
:CUSTOM_ID: one-format-one-integrity-check
:END:

BWK3 is the only envelope format bewaking writes and the only one it reads.
There is no dual path, no auto-detection and no downgrade: the version tag is
checked against the one known value before anything else is parsed, so a string
carrying any other version tag is refused at the door with the same message as
arbitrary text. A body sealed for one header does not open under another's: the
header is part of what the tag authenticates, so relabelling an envelope breaks
it rather than changing what it means.

That single path is the point: a token is opened by one code route, decode,
verify the GCM tag, then decrypt, and a body with an unexpected number of header
fields is malformed rather than "an older shape". The known format versions are
exposed as ~readable-seal-format-versions~, and today that list holds exactly one
entry.

** Tokens
:PROPERTIES:
:CUSTOM_ID: tokens
:END:

#+begin_src shell
export K1="952e0690-6c3b-4828-b191-961bf98d055c"   # encryption key
export K2="503f5869-0a3c-4460-971f-5a88662de3fc"   # signing key

# Create a token.
TOKEN=$(./bin/bewaking token generate \
  --owner-id owner-1 --owner-name Joe --owner-email joe@example.com \
  --permissions read,write --validity-seconds 3600 \
  --encryption-key "$K1" --signing-key "$K2")

# Read it back.
./bin/bewaking token decrypt --token "$TOKEN" \
  --encryption-key "$K1" --signing-key "$K2"
#+end_src

So that keys never appear in the process list, pass them from files, or export
the environment variables the CLI falls back to. Precedence is: explicit
option, then file, then environment variable. A =--keyring FILE= takes
precedence over both when given.

#+begin_src shell
export BEWAKING_ENCRYPTION_KEY="$K1"
export BEWAKING_SIGNING_KEY="$K2"

# The next commands pick the keys up automatically.
./bin/bewaking token decrypt --token "$TOKEN"
./bin/bewaking token decrypt --token "$TOKEN" \
  --encryption-key-file ./k1.txt --signing-key-file ./k2.txt
#+end_src

Sealing commands accept =--key-id LABEL= to tag the envelope for
[[#key-rotation][key rotation]], and =--keyring FILE= to select keys from an
alist of key id to key entry. Entries may carry =not-before= / =not-after=
validity windows so a rotation schedule is enforced:

#+begin_src shell
# ./keyring.scm
# (("2026a" (encryption-key . "e1") (signing-key . "s1"))
#  ("2025b" (encryption-key . "e0") (signing-key . "s0")
#           (not-after . 1790000000)))

TOKEN=$(./bin/bewaking token generate --owner-id o1 --keyring ./keyring.scm \
  --key-id 2026a)
./bin/bewaking token decrypt --token "$TOKEN" --keyring ./keyring.scm
#+end_src

** Rotation metadata and audit
:PROPERTIES:
:CUSTOM_ID: rotation-metadata-and-audit
:END:

Sealing commands can record an expiry, and every envelope's header can be read
back without any key:

#+begin_src shell
# Seal data that is only valid for an hour.
TOKEN=$(./bin/bewaking token generate --owner-id o1 \
  --encryption-key "$K1" --signing-key "$K2" --ttl-seconds 3600)

# Audit the header with no keys at all.
./bin/bewaking token inspect --token "$TOKEN"
# version:    BWK3
# key-id:     default
# created-at: 1791709670
# expires-at: 1791713270
# expired:    no

# Expired data is refused. Expiry is the one refusal that is stated in full,
# because it can only be reached once the envelope has proved genuine ...
./bin/bewaking token decrypt --token "$TOKEN" --encryption-key "$K1" \
  --signing-key "$K2"
# bewaking: failed to decrypt token (open-envelope: the sealed data expired at
#   1791713270 (key 'default').)

# ... unless you explicitly ask for it (recovery and audit only).
./bin/bewaking token decrypt --token "$TOKEN" --allow-expired \
  --encryption-key "$K1" --signing-key "$K2"

# A token whose key id you do not hold, or whose body was altered, is refused
# without saying which: one message covers every "could not open this" cause, so
# a refusal cannot be used to list the key ids a deployment configures.
./bin/bewaking token decrypt --token "$SOMEONE_ELSES_TOKEN" \
  --keyring ./keyring.scm
# bewaking: failed to decrypt token (bewaking: the sealed data could not be
#   opened: unknown, retired or wrong key, or the data was altered.)

# Or refuse anything sealed longer ago than a day.
./bin/bewaking object decrypt --input ./sealed.scm --max-age-seconds 86400 \
  --encryption-key "$K1" --signing-key "$K2"
#+end_src

The same =--ttl-seconds=, =--expires-at=, =--max-age-seconds= and
=--allow-expired= options work for =token generate=, =token decrypt=,
=object encrypt= and =object decrypt=. A failure exits with status 1. Expired
data is told apart and explained; every other refusal (an unknown key id, a
retired key, a wrong key, an altered body) is one message that names no key id
and no key material, so the CLI cannot be used to enumerate a keyring. See
[[#a-refusal-does-not-enumerate-the-keyring][A refusal does not enumerate
 the keyring]].

* Native cryptography
:PROPERTIES:
:CUSTOM_ID: native-cryptography
:END:

The module ~(bewaking crypto)~ holds the crypto primitives. They run in this
process, so there is no subprocess to spawn, no shell to quote against, and no
~PATH~ to depend on.

| Function                          | Arguments                                                                                                             | Returns                                                     |
|-----------------------------------+-----------------------------------------------------------------------------------------------------------------------+-------------------------------------------------------------|
| ~openssl-encrypt~                 | =#:plaintext=, =#:key=, =#:salt=                                                                                      | the OpenSSL-format Base64 blob                              |
| ~openssl-decrypt~                 | =#:ciphertext=, =#:key=                                                                                               | the original string (raises on bad padding)                 |
| ~hmac-sha256-hex~                 | =key=, =message=                                                                                                      | lowercase hexadecimal HMAC-SHA256                           |
| ~pbkdf2-sha256~                   | =password=, =salt=, =length=, =#:iterations=                                                                          | the derived bytes as a bytevector                           |
| ~argon2id-derive~                 | =password=, =salt=, =length=, =#:memory-kib=, =#:iterations=, =#:parallelism=                                         | the derived bytes as a bytevector                           |
| ~derive-key-material~             | =kdf=, =password=, =salt=, =length=                                                                                   | the derived bytes, for any KDF in ~kdf-spec~                |
| ~kdf-encrypt~ / ~kdf-decrypt~     | =plaintext=, =key=, =#:kdf=, =#:salt=                                                                                 | the self-describing CBC blob / the plaintext                |
| ~gcm-encrypt~ / ~gcm-decrypt~     | =plaintext=, =key=, =#:kdf=, =#:salt=, =#:nonce=, =#:associated-data= (decrypt: =sealed=, =key=, =#:associated-data=) | the Base16 authenticated payload / the plaintext bytevector |
| ~base16->bytes~                   | a hexadecimal string                                                                                                  | the decoded bytevector                                      |
| ~base16-encode~ / ~base16-decode~ | a string                                                                                                              | hexadecimal text / the decoded string                       |
| ~base64-encode~ / ~base64-decode~ | a string                                                                                                              | Base64 text / the decoded string                            |
| ~bytes->base16~ / ~bytes->base64~ | a bytevector                                                                                                          | the encoded text                                            |
| ~base64->bytes~                   | a Base64 string                                                                                                       | the decoded bytevector                                      |
| ~random-bytes~                    | =#:length= (default 8)                                                                                                | strong random bytes from libgcrypt                          |

AES-256-CBC, AES-256-GCM, PBKDF2 and Argon2id come from libgcrypt, the C library
Guile already links through =guile-gcrypt=, which publishes no Scheme bindings
for ciphers or key derivation; the module binds ~gcry_cipher_*~,
~gcry_kdf_derive~ and the stateful ~gcry_kdf_open~ / ~gcry_kdf_compute~ /
~gcry_kdf_final~ trio itself with Guile's FFI. Argon2id needs libgcrypt 1.11 or
newer, and ~argon2id-available?~ reports whether the loaded library has it.
HMAC-SHA256 uses =guile-gcrypt='s ~sign-data~, and the encodings are plain
Scheme.

#+begin_src scheme
(use-modules (bewaking crypto))

;; A deterministic blob, given a fixed salt.
(openssl-encrypt "bewaking" "mysecretkey"
                 #:salt (make-bytevector 8 0))
;; => "U2FsdGVkX18AAAAAAAAAAKkuKL+nA1jqz6ecDqWJMqc="

(base64-encode "foobar")          ; => "Zm9vYmFy"
(base16-encode "hello")           ; => "68656c6c6f"
(hmac-sha256-hex "Jefe" "what do ya want for nothing?")
;; => "5bdcc146bf60754e6a042426089575c75a003f089d2739839dec58b964ec3843"
#+end_src

*** Interoperability with OpenSSL
:PROPERTIES:
:CUSTOM_ID: interoperability-with-openssl
:END:

The AES layer of the pipeline is the format OpenSSL writes, so blobs travel in
both directions. That makes the OpenSSL CLI a convenient cross-check rather
than a requirement:

#+begin_src shell
# A blob produced by (bewaking crypto) opens with the OpenSSL CLI ...
printf %s "$BLOB" | openssl aes-256-cbc -d -pbkdf2 -a -A -base64 -k "$KEY"

# ... and a blob produced by the OpenSSL CLI opens with (bewaking crypto).
printf %s 'bewaking' | openssl enc -aes256 -pbkdf2 -a -A -k "$KEY" \
  | ... (openssl-decrypt blob "$KEY")
#+end_src

From Scheme, the same two directions are:

#+begin_src scheme
;; bewaking -> OpenSSL
(openssl-encrypt "bewaking" "mysecretkey" #:salt (make-bytevector 8 0))
;; => "U2FsdGVkX18AAAAAAAAAAKkuKL+nA1jqz6ecDqWJMqc="

;; OpenSSL -> bewaking
(openssl-decrypt "U2FsdGVkX19Ul01q1RroU5wq09nZ+ftDyRPwKRg32hSZlll8jqSu+OwtJTiS3T6J"
                 "952e0690-6c3b-4828-b191-961bf98d055c")
;; => "a secret that openssl sealed"
#+end_src

The reference values used by the test suite were generated with OpenSSL 3.5 and
Python's =cryptography=, and can be regenerated with ~openssl kdf~
(PBKDF2-HMAC-SHA256), ~openssl dgst -sha256 -hmac~ (the HMAC) and ~openssl enc~
(the AES-CBC layer). The GCM payload
format is checked byte-for-byte against =cryptography='s ~AESGCM~, under both
derivations, and the Argon2id derivation against the RFC 9106 test vector.

* Using bewaking in a web application
:PROPERTIES:
:CUSTOM_ID: using-bewaking-in-a-web-application
:END:

bewaking knows nothing about HTTP, cookies or any particular framework: it
takes a string in and hands an alist back. The same functions therefore fit
Artanis, Guile's own =web server=, a custom ~(web request)~ handler, or any
other Scheme web stack. This chapter walks through the stateless-session
pattern used in production by WikiMusic, LucidPlan and Byggsteg.

The pattern is four steps:

1. *Sign-in*: verify the password, then seal the user's details with
   ~generate-token~.
2. *Delivery*: hand the token to the client, normally in an =HttpOnly= cookie
   for browser pages and in a header for an API.
3. *Each later request*: read the token, ~decrypt-token~ it, check permissions
   and lifetime, then run the handler.
4. *Sign-out*: delete the cookie. There is no server-side session to clean up.

Because the identity travels *inside* the token, an authorized handler knows who
the caller is without a database round-trip.

** Sign-in: sealing a token into a cookie
:PROPERTIES:
:CUSTOM_ID: sign-in-sealing-a-token-into-a-cookie
:END:

The keys are read once, at startup. Names beginning with =BEWAKING_= keep the
application and the [[#command-line-interface][command-line interface]] in agreement, so an operator can
inspect and decrypt live sessions with the very same keys.

#+begin_src scheme
(use-modules (bewaking bewaking))

(define encryption-key
  (or (getenv "BEWAKING_ENCRYPTION_KEY")
      (error "BEWAKING_ENCRYPTION_KEY is not set")))
(define signing-key
  (or (getenv "BEWAKING_SIGNING_KEY")
      (error "BEWAKING_SIGNING_KEY is not set")))

(define cookie-name "x-bewaking-session")

;; Step 1: turn a verified user into a token.
(define* (issue-token #:key id email name permissions
                      (validity-seconds (* 7 24 3600)))
  (generate-token #:encryption-key encryption-key
                  #:signing-key    signing-key
                  #:token-validity-seconds validity-seconds
                  #:get-owner-details
                  (lambda ()
                    `((id . ,id)
                      (email . ,email)
                      (name . ,name)
                      (permissions ,@permissions)))))
#+end_src

Whatever the thunk returns comes back out of ~decrypt-token~ renamed to
~owner-*~: ~'id~ becomes ~owner-id~, ~'permissions~ becomes ~owner-permissions~,
and the token's own ~token-id~, ~token-created-at~ and ~token-expires-at~ fields
are added to the payload.

Step 2 is the framework's job. In an Artanis controller it looks like this:

#+begin_src scheme
;; ... verify the password, then:
(:cookies-set! rc 'x-bewaking-session cookie-name
               (issue-token #:id user-id #:email email #:name name
                            #:permissions permissions))
(:cookies-setattr! rc 'x-bewaking-session
                   #:expires (* 7 24 3600)   ; keep in step with the token
                   #:path "/"
                   #:secure #t
                   #:http-only #t)
(redirect-to rc (string->uri "/dashboard") #:status 302)
#+end_src

=#:secure= keeps the cookie off plain HTTP, =#:http-only= puts it out of reach
of JavaScript, and =#:path "/"= makes it apply to the whole site. The cookie's
lifetime should match =#:token-validity-seconds=: a cookie that outlives its
token only annoys users with "half-logged-in" states.

** Protecting a route
:PROPERTIES:
:CUSTOM_ID: protecting-a-route
:END:

One helper serves the whole application. It answers a single question, "who is
this, and are they allowed?", and returns the decrypted payload or =#f=:

#+begin_src scheme
;; The token is absent, truncated, tampered with, sealed by an unknown key,
;; expired, or lacks a needed permission: in every case we get #f.
(define* (authorized-payload #:key token (needed '()))
  (let ((payload (and (string? token)
                      (not (string-null? token))
                      (decrypt-token #:token token
                                     #:encryption-key encryption-key
                                     #:signing-key    signing-key))))
    (and payload
         (token-valid? #:token payload)
         (has-needed-permissions? #:needed needed
                                  #:present (assoc-ref payload
                                                       'owner-permissions))
         payload)))
#+end_src

Two details are worth stating. ~decrypt-token~ catches everything and returns
=#f=, so test that result *before* touching the payload; ~assoc-ref~ on =#f=
raises. And ~token-valid?~ wants the *decrypted payload*, not the token string.

A browser route reads the cookie and falls back to the login page:

#+begin_src scheme
(post "/artists/edit"
      #:cookies '(names x-bewaking-session)
      (lambda (rc)
        (let ((who (authorized-payload #:token (:cookies-value rc cookie-name)
                                       #:needed '(artist:edit))))
          (if who
              (edit-artist rc #:owner-id (assoc-ref who 'owner-id))
              (redirect-to rc (string->uri "/login") #:status 302)))))
#+end_src

One Artanis quirk is worth knowing: the route's =#:cookies '(names …)= and
~:cookies-set!~ / ~:cookies-setattr!~ use the cookie's *symbol*, while
~:cookies-value~ looks it up by *string*, hence ~cookie-name~ above.

An API route takes the token from a header instead and answers with a status
code, which suits clients that have no cookie jar:

#+begin_src scheme
(get "/api/v1/songs"
     (lambda (rc)
       ;; Artanis spells a header name as a symbol: (get-header rc 'x-bewaking-token)
       (let ((who (authorized-payload #:token (get-header rc 'x-bewaking-token)
                                      #:needed '(songs:read))))
         (if who
             (songs-as-json rc)
             (response-emit '((error . "authentication required"))
                            #:status 401)))))
#+end_src

Such a client signs in with the very same ~issue-token~ and receives the token
in a response header, rather than a cookie:

#+begin_src scheme
(post "/api/v1/login"
      (lambda (rc)
        (if (valid-credentials? rc)
            (response-emit "" #:status 204
                           #:headers `((x-bewaking-token
                                        unquote (issue-token ...))))
            (response-emit '((error . "invalid credentials")) #:status 401))))
#+end_src

Inside a handler the payload is an ordinary alist:

#+begin_src scheme
(assoc-ref who 'owner-id)          ; "144959d3-7a8e-455e-b608-31e35145a2fa"
(assoc-ref who 'owner-email)       ; "joe@example.com"
(assoc-ref who 'owner-name)        ; "Joe"
(assoc-ref who 'owner-permissions) ; (read-only manage-profile)
#+end_src

Decrypt once per request and pass the payload along, instead of calling
~decrypt-token~ again in every controller: the answer cannot change, and the
decryption is the expensive part.

Only two things are asked of a framework: read a cookie or a header, and set one.
Anything offering those two operations can use the helper above unchanged.
WikiMusic's
[[https://codeberg.org/jjba23/wikimusic/src/branch/main/lib/wikimusic/auth.scm][~bewaking-endpoint~]]
is one rendering of it, wrapped to take ~#:happy-flow~ / ~#:unhappy-flow~ thunks.

** Sealed objects: stateless state that must not be tampered with
:PROPERTIES:
:CUSTOM_ID: sealed-objects-stateless-state-that-must-not-be-tampered-with
:END:

Not everything is a session. A ~decrypt-object~ round-trip is the right tool for
short-lived state the server would otherwise have to store:

#+begin_src scheme
;; A "reset your password" link that expires in an hour, with no table row.
(define link
  (encrypt-object #:payload `((user . ,user-id) (action . reset-password))
                  #:encryption-key encryption-key
                  #:signing-key    signing-key
                  #:ttl-seconds 3600))

;; http://example.org/reset?token=<link>
;; A sealed token is Base16, dots and dashes, so it needs no escaping.
(decrypt-object #:object (assoc-ref query "token")
                #:encryption-key encryption-key
                #:signing-key    signing-key)
;; => ((user . "144959d3-...") (action . reset-password))
;; #f once the hour is over, or if the token was edited in the mail client.
#+end_src

The same pattern covers multi-step forms (seal the half-finished state into a
hidden field instead of a session record), pagination or search cursors, and
"remember my filter" preferences. Because the data is both encrypted and
authenticated, clients can neither read it nor change it, while the server stays
free of per-user state. ~encrypt-object~ takes =#:key-id= and =#:keyring=,
exactly like tokens.

** Keys, rotation and revocation
:PROPERTIES:
:CUSTOM_ID: keys-rotation-and-revocation
:END:

Keep both keys secret, keep them different from each other, and give every
environment (development, staging, production) its own pair.

Rotation needs no downtime and no forced logout. Add the new pair under a fresh
key id, start sealing with it, and keep the old entry in the keyring until the
longest-lived token sealed with it has expired:

#+begin_src scheme
(define keyring
  '(("2026a" (encryption-key . "e1") (signing-key . "s1"))
    ("2025b" (encryption-key . "e0") (signing-key . "s0"))))

;; New logins are sealed with the current key ...
(generate-token #:keyring keyring #:key-id "2026a"
                #:get-owner-details get-owner-details)

;; ... and old tokens still open, because the envelope names the key that
;; sealed it. Nothing to migrate, nobody to log out.
(decrypt-token #:token old-token #:keyring keyring)
#+end_src

Revocation is the one thing a stateless session cannot do by itself. Deleting
the cookie signs the user out of *that* browser, but a token copied beforehand
stays valid until it expires. Three ways to limit the damage, in increasing
order of cost:

- keep ~token-validity-seconds~ short for anything valuable, so the window is
  small;
- [[#enforcing-a-rotation-schedule][retire a key]] with a =not-after= window (keyring selection by =#:key-id=, or
  =--keyring FILE= on the command line). Every session sealed with that key id
  stops opening at once, the fastest "log everyone out now" switch;
- store what you care about: a payload carries its own ~token-id= (a UUID), so a
  small denylist or "sessions" table can be consulted for high-value actions
  without turning every request into a database read.

For auditing, keep the old keyring entry reachable and log the envelope header
of incoming tokens. ~envelope-metadata~ reads the version, key id and timestamps
with *no keys at all*, so the result is safe to log:

#+begin_src scheme
(envelope-metadata #:sealed token)
;; => ((version . "BWK3") (key-id . "2026a") (created-at . 1791709670)
;;     (expires-at . 1792314470)) ; #f when no #:ttl-seconds was recorded

(envelope-expired? #:sealed token) ; => #f
#+end_src

From the shell, ~./bin/bewaking token inspect --token "$TOKEN"~ prints the same
fields, so an operator can look at a suspicious cookie without holding any key.

** Checklist
:PROPERTIES:
:CUSTOM_ID: checklist
:END:

- Set =HttpOnly= and =Secure= on the session cookie, and =SameSite= if your
  framework exposes it; bewaking has no opinion on cookie policy.
- Align the cookie's lifetime with =#:token-validity-seconds=.
- Do not log tokens or keys. A token is a bearer credential: whoever holds one
  is the user, as far as the server is concerned.
- Keep session tokens out of URLs and =Referer= chains. A sealed *link* is the
  deliberate exception, because there the token is the point.
- Never trust a client-supplied user id that arrives next to a token. The
  payload is the identity; everything else in the request is a hint.
- Check permissions on the server on every request rather than building the
  permission list into a page and relying on hidden buttons.

Because a request is only "string in, value out", protected routes are easy to
test without a browser: mint a token with ~generate-token~ in the test, pass it
to the helper, and assert the payload. The project's own
[[file:test/veritas/unit/cli-spec.scm][cli-spec.scm]] exercises the same
round-trips through the command line.

* Password strength
:PROPERTIES:
:CUSTOM_ID: password-strength
:END:

A dedicated module, ~(bewaking password)~, measures and generates passwords.
It has no runtime dependency beyond Guile itself.

#+begin_src scheme
(use-modules (bewaking password))

;; Inspect the character classes present in a password.
(password-character-classes "Abc123!") ; => (lowercase uppercase digit symbol)

;; Raw entropy estimate in bits: length * log2(pool size).
(password-entropy #:password "correct horse battery staple") ; => ~131.6

;; A full report: score 0-4, label, entropy, length, classes and feedback.
(password-strength #:password "Tr0ub4dor&3")
;; => ((score . 3)
;;     (label . "strong")
;;     (entropy . 72.27)
;;     (raw-entropy . 72.27)
;;     (length . 11)
;;     (classes lowercase uppercase digit symbol)
;;     (feedback "Longer passphrases are significantly harder to crack."))

;; Convenience predicate; score 3 ("strong") or better passes by default.
(strong-password? #:password "123456")                    ; => #f
(strong-password? #:password "correct horse battery staple") ; => #t
#+end_src

*** Scoring model
:PROPERTIES:
:CUSTOM_ID: scoring-model
:END:

The estimator starts from ~password-entropy~ (length times the base-2 logarithm
of the guessing pool), then applies penalties for:

- membership in a built-in list of common passwords (this forces a score of 0),
- passwords shorter than 8 characters,
- runs of the same character (e.g. =aaaa=),
- ascending or descending sequences (e.g. =abcd= or =4321=).

The penalty-adjusted entropy maps to a score:

| Entropy (bits) | Score | Label       |
|----------------+-------+-------------|
| < 28           |     0 | very weak   |
| 28 - 39        |     1 | weak        |
| 40 - 59        |     2 | fair        |
| 60 - 79        |     3 | strong      |
| >= 80          |     4 | very strong |

This is a practical heuristic, not a formal guarantee of security. A long
passphrase of common words scores highly because it has a large search space,
even though it uses a single character class.

*** Generating strong passwords
:PROPERTIES:
:CUSTOM_ID: generating-strong-passwords
:END:

#+begin_src scheme
(generate-strong-password)                              ; 24 chars, all classes
(generate-strong-password #:length 32)                  ; custom length
(generate-strong-password #:length 16 #:include-symbols #f) ; no symbols
#+end_src

Generation guarantees at least one character from every included class, fills
the rest uniformly, then shuffles the result so there is no positional bias.
The random state is seeded from the platform at module load, giving
unpredictable output across runs.

* Explain like I'm 5: how the security works
:PROPERTIES:
:CUSTOM_ID: explain-like-i-m-5-how-the-security-works
:END:

Imagine you want to send a secret note to a friend through a post office you do
not trust, and you also want your friend to be sure the note really came from
you and was not edited on the way.

1. *You put the note in a box and lock it.* The box is locked with your
   =encryption-key=; only someone holding that key can open it. A person
   handling the mail sees a solid box, not words.
2. *You wrap the whole box in a second, different lock.* That second lock is
   the =signing-key=, a separate key on purpose: two locks, two keys, no single
   point of failure.
3. *You write a label on the outside:* who the note is for, when you made it,
   and when it should be thrown away. The second lock seals the label together
   with the box, so editing the label, say to "keep this forever" instead of
   "throw this away tomorrow", means the lock does not open at all.
4. *The whole parcel is written in a plain alphabet* (hexadecimal), so it can
   travel through email, URLs and cookies without breaking.

Five things follow from that:

- *The keys are the secret, not the method.* Everyone, including anyone reading
  this file and every line of bewaking's source code, can know exactly how the
  box is built; that is on purpose. See
  [[#what-the-source-code-gives-an-attacker][What the source code gives an
  attacker]].
- *Every box looks different.* Each seal draws fresh random numbers, so sealing
  the same note twice produces two completely different parcels, and nobody
  watching the mail can tell which two parcels carry the same note.
- *Every edit is noticed.* Change one character of the box or of the label and
  the parcel refuses to open; you cannot swap the note, correct a date, or swap
  which key the label claims was used.
- *Old parcels do not need re-sending when you rotate keys.* The label says
  which key was used, so the right key can be picked automatically (see
  [[#key-rotation][key rotation]]).
- *A parcel can be given a "throw away after" date* that the recipient's
  server checks before it opens anything, so a stolen parcel stops working on
  its own.

And the one thing this cannot do:

- *It cannot protect a weak key.* If your =encryption-key= is =hunter2=, a
  determined attacker can simply guess it. All the strength comes from the keys
  being long, random and secret, so use long random values, keep them out of
  source control, logs and screenshots, and never reuse one pair across
  development and production. See
  [[#choosing-and-keeping-keys][Choosing and keeping keys]].

* Security notes
:PROPERTIES:
:CUSTOM_ID: security-notes
:END:

- *No subprocesses, so no shell surface.* Keys and payloads are never
  interpolated into a command line; they stay in Guile values and are handed
  straight to libgcrypt. There is nothing to quote, nothing that can be read
  from ~/proc/PID/cmdline~, and nothing that a NUL byte or a quote character
  can confuse.
- *No evaluation of decrypted content.* Decrypted payloads are parsed with
  ~read~, which cannot execute code. (Guile also disables the ~#.~ read-eval
  syntax by default.) Whatever was sealed is what comes back, with no wrapper to
  interpret.
- *Malformed input is refused early.* A wrong key surfaces as a padding or
  format error before any payload is parsed, instead of being mistaken for
  valid data. Base64 and Base16 input is validated character by character.
- *Authenticity is checked explicitly, by one mechanism.* Every sealed value is
  a BWK3 envelope, and its authenticity comes from AES-256-GCM, whose tag covers
  the rotation metadata (=key-id=, =created-at=, =expires-at=) as associated
  data. There is no second verification path: a token or object that was edited
  is reported rather than silently accepted, and no field of the metadata can be
  rewritten without invalidating the seal. The format is version-tagged so it can
  evolve, and any tag other than the current one is refused outright.
- *Rotation policies are enforced, not advisory.* An envelope's =expires-at= is
  checked before its plaintext is returned (unless =#:enforce-expiry? #f= /
  =--allow-expired= explicitly asks otherwise), =#:max-age-seconds= bounds how
  old data may be, and a keyring entry's =not-before= / =not-after= window
  restricts when a key may be used. Expired data is refused rather than quietly
  decrypted, and a retired key stops opening its data at once.
- *A refusal is not an oracle.* An unknown key id, a missing keyring entry, a
  retired or not-yet-active key, a wrong key and an altered body all raise the
  same error, and the attempt is made with a placeholder key rather than
  abandoned early. Nothing about a refusal, least of all its message, names a key
  id or enumerates the keyring. Expiry is the one exception, and it is only
  reachable once the tag has shown the envelope to be genuine. See
  [[#a-refusal-does-not-enumerate-the-keyring][A refusal does not enumerate
  the keyring]].
- *Obfuscation is not security.* ~string-garble~ / ~string-ungarble~ are
  reversible by design; the real protection comes from the two independent
  AES-256 keys.
- *Key handling is the caller's responsibility.* Keep the ~encryption-key~ and
  ~signing-key~ secret and distinct. Keys are used in-process and never travel
  through a command line, so they do not appear in the process list; they are
  still ordinary Guile strings, so avoid printing or logging them.

* Choosing and keeping keys
:PROPERTIES:
:CUSTOM_ID: choosing-and-keeping-keys
:END:

Everything bewaking promises reduces to one sentence: *the keys are the secret.*
The algorithms, the formats, the source code and this document are all public,
and none of them has to be protected. A key does.

** Use long, random keys
:PROPERTIES:
:CUSTOM_ID: use-long-random-keys
:END:

The keys are ordinary strings, so nothing forces them to be strong, which is one
of the few ways to break the scheme without breaking the code. A good key is at
least 32 bytes from a cryptographically strong source:

#+begin_src shell
# 32 random bytes, hexadecimal: 64 hex characters, 256 bits.
openssl rand -hex 32
# or, without OpenSSL:
head -c 32 /dev/urandom | base16 -w 0
#+end_src

A UUID (as used in the examples above for readability) carries about 122 bits of
randomness and is acceptable; a word, a date, a project name, or a password you
can remember is not. Do not stretch a weak key by hashing it or prefixing it with
a constant; that adds no entropy. If a human-memorable secret must be the key,
seal with ~#:kdf 'argon2id~ (64 MiB, 3 passes by default) instead of the default
PBKDF2: the derivation is meant to slow a guessing attacker down, and PBKDF2's
10 000 iterations are far too cheap for a passphrase (see
[[#what-the-source-code-gives-an-attacker][What the source code gives an
attacker]]).

** Keep them secret and distinct
:PROPERTIES:
:CUSTOM_ID: keep-them-secret-and-distinct
:END:

- The ~encryption-key~ and the ~signing-key~ must be two *different* values. If
  they are equal, the inner and outer layers share a secret, and an attacker who
  learns one has learned both.
- Give every environment (development, staging, production) its own pair. A
  shared development key is a production key handed to every developer.
- Never commit a key. Not in source, not in a test, not in a config file, not in
  a container image, not in a screenshot of a terminal.
- Prefer the environment (=BEWAKING_ENCRYPTION_KEY=,
  =BEWAKING_SIGNING_KEY=) or a file (=--encryption-key-file=,
  =--signing-key-file=) over a command-line argument: environment variables and
  files are not copied into your shell history or shown in a process list.
- Do not log keys, and do not log tokens either; a token is a bearer credential.
  The exception is the envelope *header*, which ~envelope-metadata~ reads without
  any key and which carries only the key id and timestamps.

** Plan for rotation, and for compromise
:PROPERTIES:
:CUSTOM_ID: plan-for-rotation-and-for-compromise
:END:

- Give each key pair a key id and seal new data with the current one; a
  [[#key-rotation][keyring]] lets old data keep opening without a migration.
- A keyring entry's =not-before= / =not-after= window is how you retire a key:
  data sealed with it stops opening, immediately.
- If a key does leak, rotate first and investigate second: roll in a new pair,
  retire the old entry, and let short token lifetimes bound the exposure. Keys
  used in-process are not in ~ps~ output, but they may be in shell history if
  they were passed on a command line, and they are plain Guile strings in memory
  while the process runs; there is no way to wipe them, so keep the process's
  memory as uninteresting as its disk.

* What the source code gives an attacker
:PROPERTIES:
:CUSTOM_ID: what-the-source-code-gives-an-attacker
:END:

bewaking is free software. Assume the worst case, because it is the real case:
*the attacker has read every line of this repository.* They have the algorithms,
the envelope layout, the constants, the garbling routine, the test suite and the
reference vectors. They also have as many copies of any token or sealed object
they can capture, and they can edit one as much as they like. This section states
what that buys them, and what it does not.

** What they get: a clear view of a public format
:PROPERTIES:
:CUSTOM_ID: what-they-get-a-clear-view-of-a-public-format
:END:

- They can parse any token, and via ~envelope-metadata~ read its version, key id
  and timestamps *without any key*. That is deliberate: those fields are what
  rotation and log review work from, and they contain no secret.
- They know exactly which algorithms protect the data (AES-256-CBC inside,
  AES-256-GCM outside), how the keys are derived (PBKDF2 or Argon2id, and with
  which parameters, because the sealed body records them), and where every byte
  sits. None of that is a secret in a modern design; this is Kerckhoffs's
  principle, and the alternative (security through a hidden format) would be
  broken the moment somebody published the code.
- They know the obfuscation step is obfuscation. So do you: it exists to leave
  two independent encryptions between the plaintext and a reader, not to resist
  someone with a debugger.

** What they do not get: the keys, and therefore none of the values above
:PROPERTIES:
:CUSTOM_ID: what-they-do-not-get-the-keys-and-therefore-none-of-the-values-above
:END:

- *No decryption.* The body is AES-256-GCM under a key derived from the signing
  key, and the inner AES-256-CBC layer is only reached after that tag verifies.
  Without the keys, the ciphertext and any "ungarbling" the attacker performs on
  it stay ciphertext. There is no source-level shortcut to AES-256.
- *No forgery.* Every attempt starts from a genuine envelope, and the tag covers
  the ciphertext *and* the header. Flipping any digit of a real envelope,
  relabelling its version, swapping its key id, backdating =created-at=, or
  extending =expires-at= all make the tag fail; the suite checks each of these,
  including an exhaustive digit-by-digit mutation of a real token. Knowing the
  format is what makes those edits easy to *try*, and the tag is what makes each
  of them fail.
- *No swapping a body between headers.* The header is the cipher's associated
  data, so a valid body moved under a different key id, version or expiry does
  not open: the pair (header, body) is the unit that is authenticated.
- *No oracle to lean on.* A wrong key, an edited ciphertext, edited associated
  data and an unresolvable key id are indistinguishable: the envelope layer
  raises one refusal for all of them, and it raises rather than returning
  anything. The tag is checked by libgcrypt's ~gcry_cipher_checktag~ before a
  byte of plaintext is returned, the inner CBC layer's padding error is only
  reached once that tag has been accepted, and an unresolvable key id is tried
  against a placeholder instead of being answered early, so neither the padding
  error nor the keyring is a signal an attacker can probe. That is what makes a
  padding-oracle attack and keyring enumeration unavailable here rather than
  merely awkward. The raw =GCM authentication failed= text still exists for
  direct users of the ~(bewaking crypto)~ primitive, where it is the honest
  answer and no key id is involved; the envelope layer does not pass it on.
- *No code execution from decrypted data.* Payloads are parsed with ~read~, not
  ~eval~, and Guile's ~#.~ read-eval syntax is off by default (verified in the
  suite), so a sealed value cannot smuggle code into the process that opens it.
- *No shell.* There is no subprocess and no command line for a key or a payload
  to be interpolated into, so there is nothing to quote and nothing to read out
  of ~/proc=.
- *No hardcoded secret to find.* The source contains no key material: the keys
  in this document and in the test suite are labelled examples, and the suite's
  fixtures are deliberately distinct from any real pair.

** Where knowing the source does help: the honest list
:PROPERTIES:
:CUSTOM_ID: where-knowing-the-source-does-help-the-honest-list
:END:

- *Offline guessing, if the key is weak.* The source (and the sealed body) tells
  an attacker the exact derivation cost, so a low-entropy key (a passphrase, a
  pattern, a reused string) can be brute-forced offline against a captured token
  without touching your server. This is the one place source knowledge is a real
  advantage, and the whole answer is
  [[#choosing-and-keeping-keys][long random keys (or Argon2id for a
  passphrase)]].
- *A chosen key-derivation cost.* The Argon2id parameters travel inside the
  sealed body, so a crafted body can name a deliberately expensive derivation
  (up to the validated bound of 4 GiB of memory and four billion passes) and
  make the *receiver* spend that much work before the tag is even checked, so
  source knowledge turns into a small denial-of-service primitive. The bound is
  enforced *before* anything is allocated, so the worst case is capped rather
  than unbounded, but the cap is high enough to matter. The default PBKDF2 cost
  is fixed at 10 000 iterations, so tokens sealed with the default are not
  affected; if your application accepts Argon2id bodies from untrusted clients,
  keep sealing with the default, or reject tokens that arrive without a prior
  authenticated step. The suite pins this: a payload whose recorded cost is
  above the bound is refused with a parameter error (not by running the
  derivation), while a cost inside the bound is derived and then fails the tag.
- *Which key ids exist: closed.* Every "we could not open this" cause returns the
  same error, and an unresolvable key id is opened against a placeholder key
  instead of being abandoned early, so the refusal does not differ in message or
  in work. The key id still appears in the *header*, where ~envelope-metadata~
  reads it without any key, but that is a claim to log, not a decision, and it is
  not a statement about what the deployment's keyring contains.
- *Replay.* A captured, still-valid token is a bearer credential: the source
  cannot change that, because stateless sessions have no server-side list to
  revoke from. Short lifetimes, key retirement and an optional denylist are the
  mitigations, and they are matter-of-fact, not secret.

** The short version
:PROPERTIES:
:CUSTOM_ID: the-short-version
:END:

An attacker with the source, the format and any number of captured tokens, but
without the two keys, cannot read a sealed value, cannot forge one, cannot alter
one field of one, and cannot derive a key from what they hold. That is what
"the keys are the secret" means here, and it is what the suite pins down: the
sealed value leaks nothing, every edit of a genuine value is refused, and the
same plaintext never seals twice.

  altered body all produce the identical message at the library and at the
  command line, with the identical exit code, and the message names neither the
  key id nor any key material.

:PROPERTIES:

#+begin_src mermaid
graph LR

W --> V{Version tag known?}
V -- No --> R(Error)

* On Reproducibility: Why GNU Guix?
:PROPERTIES:
:CUSTOM_ID: on-reproducibility-why-gnu-guix
:END:

A build should never fail because "it worked on my machine." Reliable software development requires explicit, bit-for-bit reproducibility and a functional approach to package management and system deployment.

#+BEGIN_EXPORT html
<a href="https://guix.gnu.org/">
  <img src="https://jointhefreeworld.org/ggg/dist/gnu-guix.svg" alt="GNU Guix logo" style="max-width: 250px; width: 100%; height: auto;" />
</a>
#+END_EXPORT

- *Declarative Build Graphs:* Packages are pure functions of their inputs with no implicit system state.
- *Programmable with Guile:* Full system and package configurations written in [[https://www.gnu.org/software/guile/][Guile Scheme]] rather than rigid DSLs or static files.
- *Time Travel:* Rebuild the exact system state from any point in git history using ~guix time-machine~.
- *Atomic Operations:* Instantly upgrade or roll back environments without leaving orphaned dependencies or broken states.
- *Unified Tooling:* One tool manages development shells, isolated containers, package builds, and full system configurations.
